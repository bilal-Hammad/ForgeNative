## 2026-07-25 — HealthKit real-device verification (in progress)

- **What was done so far**: Discovered a real physical device ("Bilal iPhone", iPhone 13 Pro Max, iOS

  USB cable, and this device is connected wirelessly) — the tool that actually worked is native:
  `XCTAttachment(screenshot: XCUIScreen.main.screenshot())` captured from inside a real XCUITest run
  on the device itself, extracted afterward via `xcrun xcresulttool export attachments`.
- **Judgment calls**: Added "Steps" and "Sleep" to the debug tool's test-habit set specifically so the

- **What was verified, and how**: Real screenshots (via the `XCTAttachment` technique above) confirmed:
  (a) the real system "Health Access" consent sheet genuinely appears when `requestAuthorization` is
  called on-device (not just in theory); (b) the "Allow" button renders visually disabled/grayed until
  at least one write toggle is turned on — confirmed by comparing before-tap and after-tap screenshots
  that looked identical, ruling out "mid-animation" as the explanation; (c) after fixing the test to
  tap "Turn On All" before "Allow", the write toggles in the follow-up screenshot were **still off** —
  meaning the tap itself wasn't registering, not that the button was structurally unreachable; (d)
  XCTest's own auto-captured accessibility-hierarchy dump (attached automatically on the failed query)
  showed Forge's own prior debug screen content at the exact moment the query for "Turn On All" ran —
  while the `XCUIScreen` screenshot taken at essentially the same moment correctly showed the consent
  sheet. This is the key finding: the system consent sheet is visually composited on screen (so raw
  screenshots see it) but is not part of `XCUIApplication()` (scoped to Forge's own bundle ID)'s
  accessibility tree at all — a process/tree boundary, not a hit-testing timing gap as the prior
  session's Simulator-only investigation concluded. This reproduces identically on real hardware, which
  the prior session did not have access to test against.
- **Conclusive result — this is a confirmed hard blocker, not assumed after one attempt.** Tried three
  genuinely different technical approaches, in order: (1) `XCUIApplication()` scoped to Forge's own
  bundle ID — found a match in one Simulator attempt (via a loose label predicate) but taps never
  actually registered on real device, confirmed via before/after screenshots showing zero state change;
  (2) `XCUIApplication(bundleIdentifier: "com.apple.springboard")` — no match at all
  (`SPRINGBOARD_TURN_ON_ALL_NOT_FOUND`, `SPRINGBOARD_ALLOW_NOT_FOUND`); (3) a raw OS-level mouse click
  via `cliclick` at the button's actual on-screen pixel coordinates (bypassing XCUITest's accessibility
  layer entirely, querying the Simulator window's real screen position via System Events) — blocked
  before it could even run: `System Events` reported 0 windows for the Simulator process despite a
  device being genuinely booted and the app genuinely running, which points at missing macOS
  Accessibility permission for GUI scripting in this environment — itself something requiring one-time
  manual approval in System Settings → Privacy & Security → Accessibility, the same category of
  "needs a human physically present" problem this was trying to route around.
  The precise mechanism (established via XCTest's own auto-captured accessibility-hierarchy dump,
  compared against a same-moment `XCUIScreen` pixel screenshot showing genuinely different content):
  the real system "Health Access" consent sheet is visually composited on screen but is not part of
  the requesting app's own accessibility tree — a process/tree boundary, not a Simulator-only
  hit-testing timing gap as an earlier session's narrower investigation concluded. This is consistent
  with Apple's own well-known stance on privacy-consent UI (Health, Photos, Contacts, Location, etc.)
  being deliberately non-automatable via XCUITest from the requesting app's own test target, precisely
  so apps can't script past user consent.
